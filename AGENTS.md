# Backend agent notes

- Workspace-wide premise and decision principles live in `../Context.md`; cross-project ownership, generation workflow, and client-customization rules live in `../WORKSPACE.md`. Keep this repository's `README.md` focused on backend setup and behavior.
- This repository is the runnable Spring Boot backend. Liquibase is authoritative for the physical database schema; do not rewrite executed change sets.
- Keep `app.core` free of concrete classes. Shared infrastructure belongs in responsibility-owned subpackages: `configuration`, `exception`, `pagination`, `persistence`, `referenceData`, and `security`.
- Model only current contracts. Do not add compatibility aliases, duplicate legacy fields, fallback mappings, or transitional runtime layers.
- This is a showcase application whose local database may be deliberately dropped and recreated. If the Liquibase baseline or change-set IDs are intentionally regenerated, use a fresh database; retained databases still require immutable executed change sets.
- Reference lookup entities `Sexe`, `SituationFamiliale`, and `TypeConge` use database `id` as identity and `libelle` as the display value; add a separate `code` only when a stable cross-system business key is required.
- Bounded SQL strings such as `nvarchar(250)` keep their physical size in Liquibase. Mirror that limit with `@Size(max = 250)` only on independently writable request DTO fields, except `description` fields, which intentionally remain without `@Size`; do not duplicate the limit with entity-level `@Size` or generated-domain `@Column(length = 250)` metadata.
- Employee filter search text has a deliberate request limit of 250 characters except for `description`; keep the optional filter body `@Valid` while allowing a null body and one-sided date ranges.
- Entity-specific DTO ID aliases (`idEmploye`, `idDepartement`, and similar) remain writable and must not be marked `JsonProperty.Access.READ_ONLY`; canonical `id` owns path/body consistency.
- API-facing DTO identifiers keep their Java `Long` type and use `app.core.configuration.JsonId`, which serializes only annotated IDs as JSON strings. Path variables and repositories remain `Long`; frontend models remain `string`. Do not apply this annotation to counters or other numeric values, introduce `BigInteger` merely to distinguish IDs, or add DTO conversion mappers for this boundary; keep generated DTO ID annotations synchronized through the engine.
- Generated Java imports follow the IDE-compatible group order `java`, `javax`, `org`, `com`, then all remaining packages alphabetically. Preserve deliberate multiline records through formatter settings (`join_wrapped_lines=false`, or record-component alignment `49` when every record should wrap), not end-of-line comments added solely to block formatting.
- `POST /api/login` accepts usernames up to 50 characters and passwords up to 256 characters and returns only `accessToken`; these are request bounds, not persistence metadata. Administrative account create/reset requests additionally require passwords of at least 8 characters and reject values above BCrypt's 72-byte UTF-8 limit before encoding.
- Under `app.core.security`, the `account` subpackage owns the account entity, role, persistence, DTO, service, and administration resource; the `login` subpackage owns password login and JWT authentication. Shared HTTP security configuration belongs in `app.core.configuration`; security exception handling belongs in `app.core.exception`. Keep the `app.core.security` package root free of concrete classes.
- Keep `Account` names for persistence and account administration. `LoginResource`, `LoginPrincipal`, and `LoginPrincipalLoader` own password login, its Spring Security snapshot, and its loading adapter.
- Each `Account` has exactly one role. Authenticated identity is carried by the JWT `sub` and scalar `role` claims; do not add an endpoint that merely echoes those claims. `ROLE_GESTIONNAIRE_RH` owns the complete `/api/rh/**` namespace; `ROLE_ADMIN` owns only `/api/admin/accounts/**`. Keep new RH entities under the shared namespace rather than enumerating entity routes in security configuration. Do not introduce a role hierarchy or give administrators implicit business access; a person needing both contexts uses two accounts.
- The security baseline is intentionally consolidated around singular roles and seeds separate `admin` and `gestionnaire-rh` showcase accounts. Use a fresh disposable database after this baseline change, and replace both accounts before a client migration.
- JSON role values use canonical enum strings only. Keep `AppRole`'s delegating JSON creator strict so numeric ordinals, arrays, lowercase names, and unknown strings can never assign security roles.
- Account role, activation, and password changes increment the token version. Authenticated JWT requests must require a positive integral `aid`, a non-negative integral `ver`, and one canonical scalar `role`, then check the current account ID, activation, role, and token version so security changes revoke old tokens immediately.
- Keep the Base64 JWT signing secret scoped to the `SecurityConfiguration` key-producing bean. Do not add it to `JwtProperties` or another value object whose generated representation could expose it.
- Account administration does not hard-delete accounts, prevents an administrator from changing/deactivating their own role, and must preserve at least one active administrator under the repository locks.
- JSON request members that are absent from the target DTO are ignored globally. API `LocalDate` values use the `spring.jackson.date-format` pattern (`dd/MM/yyyy`); Spring Boot 4's standard date-format setting does not apply it to `LocalDate`, so keep the `JsonConfiguration` type override synchronized with that property.
- Service-level cross-field and business validation uses typed private static `validate(...)` entry points. Bean Validation annotations remain responsible for request-field shape validation.
- Shared reference-data query mechanics live in `app.core.referenceData`. The client-specific route and catalog belong to the domain, such as `app.domain.rh.referenceData.RhReferenceDataResource` and `RhReferenceDataCatalog`.
- Spring Boot's default Problem Details advice can run before an unordered application advice. Field-level request validation is therefore handled by the validation-only, highest-precedence `ValidationExceptionHandler`; do not raise the precedence of the broad `ApiExceptionHandler`, because normal framework 404/405 handling and response headers must remain intact.
- Resources rely on core advice for application exceptions (`NoSuchElementException` and `IllegalArgumentException`) and on Spring Boot for ordinary built-in MVC errors; keep resource-owned path/body mismatch checks and optional lookup 404s explicit.
- Full-stack E2E orchestration belongs in the sibling `../crud-e2e` project, which is currently only a planning scaffold. In this repository, `./mvnw test` compiles the backend and runs focused account-policy, JWT-invalidation, role-JSON, JSON-ID, route-matrix, and changelog-validation tests.
