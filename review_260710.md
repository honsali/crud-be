# Executive verdict

This is already a **good, unusually clean CRUD showcase**: explicit feature packages, DTOs, mappers, transactional services, Liquibase, lazy relations, bounded pagination, safe filtering, stateless security, and very little unnecessary framework code.

This repository is a **tailor-style executable template**, not an application intended to be deployed directly. For a new client, the backend and tied frontend are copied and launched to verify the environment; the RH domain and its showcase data are then removed and replaced with the generated client domain and client data. The production baseline is the resulting client project, not this unchanged RH showcase.

It is **not yet ready to be reused as the foundation for every production client project**. The main gaps are not “more architecture”; they are:

1. no executable test safety net;
2. several confirmed Spring Security 7/JWT contract defects;
3. no automated proof that client generation completely replaces the RH domain and data;
4. incomplete API contract ownership;
5. unsafe local/reset configuration;
6. improvements not yet propagated into the generator.

My recommendation is to keep the current architecture and harden the template and tailoring workflow—not replace them with hexagonal layers, generic CRUD bases, microservices, or enterprise tooling.

This document began as a read-only review. Implementation progress is recorded in the relevant numbered sections below; points 2 through 6 were implemented and runtime-verified on 2026-07-10, and point 7 was reclassified after clarifying the template workflow.

# P0 — release gate

## 1. Add a real test suite before further modernization

There is no `src/test` and no test dependency in `pom.xml`. A successful Maven build currently proves compilation only.

Add:

- `spring-boot-starter-test`
- `spring-security-test`
- `spring-boot-testcontainers`
- the Boot-managed PostgreSQL Testcontainers module

Use PostgreSQL, not H2.

### Minimum high-value tests

1. **Migration and tailoring test**
   - fresh RH showcase migration contains the expected showcase fixtures;
   - second migration is a no-op;
   - generated client output contains no residual RH changelog, CSV, entity, or master-changelog include;
   - a fresh generated-client migration contains exactly the intended client bootstrap data;
   - Hibernate schema validation succeeds.

2. **Security test**
   - missing, malformed, short secret startup failures;
   - valid, expired, wrong-signature, wrong-algorithm and wrong-issuer JWTs;
   - token claim contains only application authorities;
   - USER/ADMIN authorization rules;
   - inactive and invalid users get indistinguishable responses;
   - CORS allowed/disallowed origins.

3. **API error contract**
   - `400/401/403/404/405/406/409/415/500`;
   - `application/problem+json`;
   - validation field errors;
   - sanitized server failures.

4. **Representative CRUD integration**
   - employee create/read/update/delete;
   - referenced entity resolution;
   - leave child workflow;
   - uniqueness and FK conflicts.

5. **Filtering/pagination**
   - `%`, `_`, `\` escaping;
   - inclusive date ranges;
   - stable tie-break sorting;
   - sort allowlist;
   - page-size cap.

A single CI job running `./mvnw -B -ntp clean verify` is enough for a solo project.

# P1 — security corrections

## 2. Stop copying Spring Security factor authorities into JWT roles

**Status: implemented and runtime-verified on 2026-07-10.** JWT issuance, JWT authority conversion, and `/api/user` now retain only distinct `ROLE_*` application authorities. `FACTOR_PASSWORD` and `FACTOR_BEARER` remain internal Spring Security details and are not exposed. Polluted legacy JWT claims were also verified to be filtered.

`AuthResource.java:42-49` originally copied every authority from password authentication into the JWT. Spring Security 7 automatically adds `FACTOR_PASSWORD`.

The resource server then adds `FACTOR_BEARER`. Consequently, `/api/user` currently returns something like:

```json
{
  "roles": [
    "ROLE_USER",
    "FACTOR_PASSWORD",
    "ROLE_ADMIN",
    "FACTOR_BEARER"
  ]
}
```

These are authentication-mechanism markers, not application roles.

### Change

- When issuing a JWT, include only recognized application authorities, such as `ROLE_*`.
- In `UserResource`, return only application roles/permissions.
- Do not preserve `FACTOR_PASSWORD` inside a long-lived bearer token unless implementing a deliberate MFA/step-up design.
- Sort roles deterministically.

There is also a frontend integration issue: `../crud-fe/src/waxant/noyau/auth/ContexteAuth.tsx:83` selects the first recognized authority. Because `ROLE_USER` precedes `ROLE_ADMIN`, an admin may be normalized to the invite role. It should use the backend’s explicit `role` field or apply deterministic role precedence.

---

## 3. Actually enforce roles

**Status: implemented and runtime-verified on 2026-07-10 with the selected project policy.** `POST /api/authenticate` is public; every other `/api/**` route requires `ROLE_USER` or `ROLE_ADMIN`. Both roles retain equal CRUD access by default. Tokens with no role, only `FACTOR_*`, or an unknown role receive `403`. Method security is enabled so a focused `@PreAuthorize("hasRole('ADMIN')")` can be added when a concrete business rule requires it; no endpoint is currently ADMIN-only.

The original `.authenticated()` rule accepted a signed token without an application role. The implemented rule now requires a recognized application role without introducing a generic permission engine.

---

## 4. Complete JWT validation and fail at startup

**Status: implemented and runtime-verified on 2026-07-10.** Security properties now validate nonblank issuer/audience and a token lifetime of `1..604800` seconds. Explicit HS512 secrets must be strict Base64 and decode to at least 64 bytes. Issuer, audience, timestamp, signature, and algorithm checks are enforced. Wrong/missing issuer or audience and expired tokens return `401`; invalid configuration fails startup. The ignored `rememberMe` component was removed while the existing `id_token` response remains compatible.

### Confirmed problems from the initial review

- `AuthResource.java:26` emits issuer `app_core`.
- `SecurityConfiguration.java:93-97` does not validate it.
- A wrong-issuer token signed with the dev key was accepted.
- A three-byte HS512 key allowed startup and produced a `500` only during login.
- Token validity can be zero, negative, or unreasonably large.
- `rememberMe` is accepted but ignored.

### Implemented change

- Added validated `@ConfigurationProperties` for the secret, issuer, audience, and bounded token-validity seconds.
- Centralized signing and decoding on one validated `SecretKey` bean.
- Configured timestamp, issuer, and audience validation with Spring Security validators.
- Removed the ignored `rememberMe` input component.

A future coordinated API/frontend change may rename `id_token`. This token authorizes API calls, so it is an **access token**, not an OpenID Connect ID token. A conventional response would contain `access_token`, `token_type`, and `expires_in`.

---

## 5. Harden local authentication

**Status: implemented and revised for the single-production workflow on 2026-07-10.** The committed fallback and temporary JWT mechanisms were removed. Every launch, including the laptop, now requires the same explicit validated `APP_SECURITY_JWT_BASE64_SECRET` policy as the server. Missing, malformed, or short secrets fail startup.

The initial review found that the fixed dev secret and confirmed `admin/admin` login were profile-guarded but potentially reachable because the server listened on all interfaces.

The laptop and server now use the same base configuration with no `dev`/`local` Spring profiles. Deployment values such as the database URL, JWT secret, CORS origins, and optional bind address remain external configuration. Login throttling remains a deployment-edge responsibility. BCrypt cost 12 is retained.

---

## 6. Make security failures use the API error contract

**Status: implemented and runtime-verified on 2026-07-10.** MVC authentication failures and security-filter authentication/access-denial failures now return sanitized `application/problem+json` responses with stable `code` properties. Bearer challenges retain Spring Security's `WWW-Authenticate` headers. Wrong credentials and unknown users return the same fixed public message without exposing exception text.

Previously:

- MVC authentication failure returns Problem Details;
- bearer authentication failure returns an empty `401`;
- access denial/filter failures may use another representation;
- wrong credentials expose locale-dependent Spring text—French on this machine.

Add an authentication entry point and access-denied handler that:

- preserve `WWW-Authenticate`;
- return sanitized Problem Details;
- expose a stable machine-readable error code;
- never return raw `AuthenticationException.getMessage()`.

Use a fixed public message such as `Invalid username or password.`

# P1 — database and migrations

## 7. Ensure tailoring completely replaces the showcase domain and data

**Status: the original production-fixture finding is not applicable by design; reclassified as a tailoring-workflow concern on 2026-07-10.** Unconditional RH CSV loading is intentional in this repository: departments, employees, lookup values, and leave data make the disposable showcase immediately functional after the backend and frontend are copied. This unchanged RH application is not the production deliverable.

The required invariant is that tailoring a client project completely replaces the RH overlay:

- remove RH entities, DTOs, mappers, repositories, services, resources, and frontend artifacts;
- remove RH Liquibase changelogs, CSV files, constraints, and every RH include from `master.xml`;
- generate the real client domain and the intended client data;
- recreate and migrate a fresh client database rather than promoting the disposable showcase database;
- verify automatically that no RH package, table, changelog, CSV, route, or frontend module remains.

Generated client data may legitimately be unconditional when it is genuine client bootstrap/reference data intended for deployment. Add a `BASELINE`/`DEMO` seed distinction only if a client project contains both production seed data and temporary fake verification records; the generator does not need that abstraction merely to classify this RH showcase.

Once a generated client changelog has reached a persistent environment, normal Liquibase immutability rules apply: do not rewrite executed change sets casually; append corrective migrations or create a deliberate new baseline.

## 8. Remove destructive switches from the normal path

**Status: implemented on 2026-07-10.** The shared Liquibase `drop-first` switch was removed, so normal application startup no longer exposes a project-configured reset path. The former `init.sql` is now the explicitly named `reset-local-db.sql`; it remains available for intentional generator testing against the disposable local database.

Run `reset-local-db.sql` manually when a clean showcase database is required. It drops and recreates the entire PostgreSQL `public` schema, so verify the target database before executing it.

---

## 9. Define production administrator provisioning

**Status: implemented for the solo, single-production tailoring workflow on 2026-07-10.** Liquibase loads `app_user.csv` automatically once during the initial database migration. Before the first migration of the tailored client/server database, replace the showcase username and BCrypt hash in that CSV with the unique client administrator credential, then start the server normally.

The clear password is never stored. A BCrypt cost-12 hash can be generated externally with `htpasswd`; Liquibase records the seed change set so later startups do not insert it again. Never deploy the showcase `admin/admin` credential. If a persistent database has already executed the change set, do not edit the CSV expecting an update—add a new migration or provision the account deliberately.

Account creation, password-change, and forgotten-password endpoints remain optional business features rather than prerequisites for first-administrator provisioning. For public-facing projects, external OIDC may be preferable, but it should not be bundled into every generated client by default.

## 10. Add concurrency protection

**Status: not applicable by design for the current solo/small-client scope.** These applications have little simultaneous editing and accept last-write-wins behavior. Adding `@Version`, DTO version fields, frontend propagation, and stale-write handling would add contract complexity without enough practical benefit.

Reconsider optimistic locking only for a client with frequent concurrent editing or financial, legal, or otherwise critical records.

---

## 11. Add missing indexes and integrity rules

**Status: implemented on 2026-07-10.** Liquibase now creates indexes for generated foreign-key columns, including the composite `(employe_id, code)` leave-list index. The generator emits these indexes for reference and father relationships.

Explicit-ID data loads are followed by PostgreSQL sequence synchronization, `app_user` has case-insensitive `lower(username)` uniqueness, and leave dates have a database check ensuring the end date is not before the start date. Hibernate now starts with `ddl-auto: validate` after Liquibase.

The date-order rule is explicit RH DSL metadata rather than a guessed universal rule. Speculative text/trigram indexes remain excluded and should be introduced only after measurement.

# P1/P2 — API contract

## 12. Own the page JSON instead of serializing `PageImpl`

**Status: stable page contract implemented and runtime-verified on 2026-07-10.** Public paginated resources now return the application-owned `PageResponse<T>` instead of serializing Spring Data `PageImpl`. Its flat fields exactly match the existing frontend contract: `content`, `totalElements`, `totalPages`, `size`, `number`, `numberOfElements`, `first`, and `last`.

The generator wraps filter, paginated-list, and find resource responses while keeping Spring Data `Page` internal to repositories and services. The employee filter returned the expected JSON at runtime without Spring Data’s unstable-page warning, so no frontend change was required. Unused `Link` and `X-Total-Count` CORS exposure was removed.

Related future scaling work remains optional: paginate leave collections and large employee reference lists when client data sizes justify it. Static, genuinely small lookup lists may remain unpaged.

## 13. Validate and map sort properties

Spring Data documentation states that sort properties arrive as unvalidated strings and applications are responsible for checking them.

`PageableUtils` provides stable ordering, which is good, but arbitrary persistence property names still reach JPA.

Generate a small per-resource mapping:

```text
public API name -> entity property
```

Reject everything else with `400`. Keep the `id` tie-breaker.

## 14. Fix the Problem Details ownership conflict

Static inspection suggested the catch-all might convert framework errors to `500`, but runtime proved that Boot’s `ProblemDetailsExceptionHandler` currently wins:

- bad ID → `400`;
- unknown route → `404`;
- wrong method → `405`.

However, this also means your custom handlers for:

- `MethodArgumentNotValidException`;
- `HttpMessageNotReadableException`;

are bypassed. Blank login produced no custom `fields` property.

Choose one approach:

1. accept Spring Boot’s default Problem Details and delete the dead custom handlers; or
2. own the contract by extending `ResponseEntityExceptionHandler`, overriding the desired methods, and adding explicit ordering.

Do **not** simply give the current advice highest precedence: its catch-all could then turn framework errors into `500`.

Add a stable `code` property and preserve `status`, `title`, `detail`, `instance`, and field violations.

---

## 15. Align validation, JPA and Liquibase

Liquibase strings are generally 250 characters, while DTOs lack `@Size` and JPA columns default to 255.

Generate matching metadata:

- DTO `@Size(max = 250)`;
- entity `@Column(length = 250)`;
- Liquibase `varchar(250)`.

Then a 251-character request becomes a field-level `400`, not a database `409`.

Use DSL semantics:

- `Email("email")` should generate `@Email`;
- ordinary `Text` should not;
- leave/date ordering belongs to the HR model;
- avoid guessing universal business validation.

---

## 16. Simplify DTO identity and references

Current DTOs expose both:

```text
id
idEmploye / idConge / idDepartement / ...
```

Only `id` is consistently honored, so contradictory requests are possible.

Full DTOs are also reused as compact references, even though reference mappers deliberately set fields annotated `@NotBlank` to null.

Target design:

- one canonical server-owned ID;
- transitional aliases marked read-only if frontend compatibility requires them;
- a truthful compact reference DTO;
- relation input that clearly requires an ID;
- coordinated frontend/generator migration.

Do not create a large DTO hierarchy. One small reference type and an explicit mutable version field are enough.

---

## 17. Add smaller REST improvements

Worth doing after the preceding items:

- remove repetitive controller `try/catch` blocks and centralize translation;
- use explicit `NotFoundException`/`BadRequestException` rather than broad `NoSuchElementException` and `IllegalArgumentException`;
- add `Location` to successful POST responses;
- standardize the leave collection path on a breaking release;
- make package names lowercase in newly generated projects;
- normalize or deliberately preserve whitespace/case for codes and natural keys.

API versioning, PATCH, idempotency keys and HATEOAS are not currently justified.

# Configuration, build and operations

## 18. Use one configuration model on the laptop and server

**Status: profile simplification implemented on 2026-07-10.** The `dev`/`local` Spring profiles were removed. The laptop and the single client server run the same application configuration and data model; only externally supplied deployment values differ.

Keep `application.yml` as the single configuration source with:

- datasource values overridable through environment variables;
- explicit JWT secret configuration required everywhere;
- configurable CORS origins and optional server bind address;
- no `drop-first`;
- identical Liquibase behavior and initial data on laptop and server.

Replace remaining scattered `@Value` fields with validated configuration records where useful.

# Generator changes

The generated conventions should be fixed in `../engine`, not only in the copied backend.

Relevant ownership:

| Concern | Generator surface |
|---|---|
| DTO IDs, references, version, validation | `BeDtoPrinter`, field implementations |
| JPA lengths | `Field`, `Text`, `Email`, `BeDomainPrinter` |
| Client seed replacement and sequence synchronization | `BeLiqTablePrinter`, `BeLiqDataPrinter` |
| FK indexes/check constraints | `BeLiqConstraintPrinter` |
| Controller exception duplication | CRUD `*ResourceInjection` classes |
| Stable page response/sort allowlist | filter/list injections |
| Reference-data registry | generate from `ReferenceData` metadata |
| Project package/app/issuer/database names | a small generator project-settings input |

The current `ReferenceDataService` is allowlisted and not directly injectable, but it is domain-specific, stringly typed runtime code under `app.core`. Generate an explicit switch/repository implementation instead of dynamic entity/property JPQL.

Also add generator verification:

1. clean deterministic generation;
2. golden output comparison;
3. assert that a tailored client output contains no residual RH backend/frontend artifact, migration include, table, or CSV;
4. merge the generated backend overlay with `crud-be`;
5. compile it;
6. run its Liquibase migration and intended client bootstrap data against PostgreSQL;
7. assert a second generation is byte-stable.

The engine’s comparator-first workflow is good and should be retained.

# Features to keep

Do not lose these strengths:

- package-by-feature domain slices;
- direct, hand-editable generated Java;
- DTO/entity separation;
- service transaction boundaries;
- dirty checking;
- `open-in-view: false`;
- lazy relations;
- entity graphs on collection queries;
- stable pagination tie-breaking and max page size;
- correctly escaped LIKE filters;
- database-backed uniqueness and foreign keys;
- no dangerous cascade deletion;
- Liquibase as the only schema owner;
- stateless bearer authentication;
- exact CORS origins and no credentialed CORS;
- BCrypt cost 12;
- fail-closed production JWT secret;
- sanitized unexpected errors;
- compact Boot-managed dependency set.

---

# Features not to add by default

Avoid turning “best” into “largest”:

- generic base CRUD controllers/services/repositories;
- reflection-driven mappers or reference registries;
- microservices;
- reactive WebFlux for a JDBC application;
- Lombok or MapStruct merely to shorten generated output;
- H2 integration tests;
- generic RBAC engines;
- refresh/revocation infrastructure without a requirement;
- cache, auditing or notifications in every project;
- Kafka/event buses;
- Kubernetes/Helm/service mesh;
- SonarQube, mutation testing or blanket coverage percentages;
- OpenAPI unless an independent client needs it;
- native images without a measured deployment benefit.

Auditing may be essential for a real HR project, but it is a domain/compliance decision, not a universal CRUD starter feature.

# Suggested implementation order

## Phase 1 — verification first, 1–2 days

- test dependencies;
- PostgreSQL Testcontainers;
- security/migration/error/CRUD/filter tests;
- one CI `clean verify` job.

## Phase 2 — immediate hardening, 1–2 days

- filter factor authorities;
- enforce USER/ADMIN rules;
- validate issuer/key/lifetime;
- one explicit laptop/server configuration model;
- required JWT secret in every environment;
- automated verification that tailoring removes the RH domain and data;
- safe administrator bootstrap;
- remove destructive reset paths.

## Phase 3 — API and persistence correctness, 2–4 days

- stable page response;
- sort allowlists;
- DTO/JPA/Liquibase length alignment;
- FK indexes and date checks;
- truthful reference DTOs;
- centralized Problem Details.

## Phase 4 — generator propagation, 2–5 days

- update engine printers/injections;
- generate reference support;
- introduce project settings and client seed replacement rules where needed;
- golden generation, no-residual-RH, and host-compilation tests;
- coordinate frontend ID/page/role changes.

A focused solo developer could bring the core baseline to a strong production standard in roughly **one to two weeks**, without adding enterprise ceremony.
