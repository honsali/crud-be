# Executive verdict

This is already a **good, unusually clean CRUD showcase**: explicit feature packages, DTOs, mappers, transactional services, Liquibase, lazy relations, bounded pagination, safe filtering, stateless security, and very little unnecessary framework code.

It is **not yet ready to be the reusable production baseline for every new project**. The main gaps are not “more architecture”; they are:

1. no executable test safety net;
2. several confirmed Spring Security 7/JWT contract defects;
3. demo data mixed with production migrations;
4. incomplete API contract ownership;
5. unsafe local/reset configuration;
6. improvements not yet propagated into the generator.

My recommendation is to keep the current architecture and harden it—not replace it with hexagonal layers, generic CRUD bases, microservices, or enterprise tooling.

This document began as a read-only review. Implementation progress is recorded in the relevant numbered sections below; points 2 through 5 were implemented and runtime-verified on 2026-07-10.

# P1 — security corrections

## 2. Stop copying Spring Security factor authorities into JWT roles

**Status: implemented and runtime-verified on 2026-07-10.** JWT issuance, JWT authority conversion, and `/api/user` now retain only distinct `ROLE_*` application authorities. `FACTOR_PASSWORD` and `FACTOR_BEARER` remain internal Spring Security details and are not exposed. Polluted legacy JWT claims were also verified to be filtered.

`AuthResource.java:42-49` originally copied every authority from password authentication into the JWT. Spring Security 7 automatically adds `FACTOR_PASSWORD`.

The resource server then adds `FACTOR_BEARER`. Consequently, `/api/user` currently returns something like:

```json
{
  "roles": [
    "ROLE_USER",
    "FACTOR_PASSWORD",
    "ROLE_ADMIN",
    "FACTOR_BEARER"
  ]
}
```

These are authentication-mechanism markers, not application roles.

### Change

- When issuing a JWT, include only recognized application authorities, such as `ROLE_*`.
- In `UserResource`, return only application roles/permissions.
- Do not preserve `FACTOR_PASSWORD` inside a long-lived bearer token unless implementing a deliberate MFA/step-up design.
- Sort roles deterministically.

There is also a frontend integration issue: `../crud-fe/src/waxant/noyau/auth/ContexteAuth.tsx:83` selects the first recognized authority. Because `ROLE_USER` precedes `ROLE_ADMIN`, an admin may be normalized to the invite role. It should use the backend’s explicit `role` field or apply deterministic role precedence.

---

## 3. Actually enforce roles

**Status: implemented and runtime-verified on 2026-07-10 with the selected project policy.** `POST /api/authenticate` is public; every other `/api/**` route requires `ROLE_USER` or `ROLE_ADMIN`. Both roles retain equal CRUD access by default. Tokens with no role, only `FACTOR_*`, or an unknown role receive `403`. Method security is enabled so a focused `@PreAuthorize("hasRole('ADMIN')")` can be added when a concrete business rule requires it; no endpoint is currently ADMIN-only.

The original `.authenticated()` rule accepted a signed token without an application role. The implemented rule now requires a recognized application role without introducing a generic permission engine.

---

## 4. Complete JWT validation and fail at startup

**Status: implemented and runtime-verified on 2026-07-10.** Security properties now validate nonblank issuer/audience and a token lifetime of `1..604800` seconds. Explicit HS512 secrets must be strict Base64 and decode to at least 64 bytes. Issuer, audience, timestamp, signature, and algorithm checks are enforced. Wrong/missing issuer or audience and expired tokens return `401`; invalid configuration fails startup. The ignored `rememberMe` component was removed while the existing `id_token` response remains compatible.

### Confirmed problems from the initial review

- `AuthResource.java:26` emits issuer `app_core`.
- `SecurityConfiguration.java:93-97` does not validate it.
- A wrong-issuer token signed with the dev key was accepted.
- A three-byte HS512 key allowed startup and produced a `500` only during login.
- Token validity can be zero, negative, or unreasonably large.
- `rememberMe` is accepted but ignored.

### Implemented change

- Added validated `@ConfigurationProperties` for the secret, unsafe-development flag, issuer, audience, and bounded token-validity seconds.
- Centralized signing and decoding on one validated `SecretKey` bean.
- Configured timestamp, issuer, and audience validation with Spring Security validators.
- Removed the ignored `rememberMe` input component.

A future coordinated API/frontend change may rename `id_token`. This token authorizes API calls, so it is an **access token**, not an OpenID Connect ID token. A conventional response would contain `access_token`, `token_type`, and `expires_in`.

---

## 5. Harden local authentication

**Status: implemented and runtime-verified on 2026-07-10.** The committed fallback secret was removed. With no explicit secret, the existing unsafe flag plus `dev`/`local` profile now creates one random 64-byte signing key per process and logs no key material. Dev/local profiles bind to `127.0.0.1` by default, with `SERVER_ADDRESS` as the deliberate override. A token works in its issuing process and returns `401` after restart; invalid explicit secrets never fall back.

The initial review found that the fixed dev secret and confirmed `admin/admin` login were profile-guarded but potentially reachable because the server listened on all interfaces.

The local profile now binds to loopback, uses one shared ephemeral key, preserves the explicit opt-in, and permits a deliberate `SERVER_ADDRESS` override for Docker or LAN testing. Production continues to require an explicit validated secret.

Login throttling remains a deployment-edge responsibility. BCrypt cost 12 is retained.

---

## 6. Make security failures use the API error contract

Currently:

- MVC authentication failure returns Problem Details;
- bearer authentication failure returns an empty `401`;
- access denial/filter failures may use another representation;
- wrong credentials expose locale-dependent Spring text—French on this machine.

Add an authentication entry point and access-denied handler that:

- preserve `WWW-Authenticate`;
- return sanitized Problem Details;
- expose a stable machine-readable error code;
- never return raw `AuthenticationException.getMessage()`.

Use a fixed public message such as `Invalid username or password.`

# P1 — database and migrations

## 7. Separate schema, required reference data, and demo fixtures

Only `security_table.xml:33` marks its seed as `@dev`. Other CSV loads are unconditional:

- `departement_table.xml:26-35`
- `employe_table.xml:62-83`
- lookup-table changelogs
- `conge_table.xml:38-51`

That means a production migration receives showcase employees and departments.

Split data into:

1. schema;
2. genuine mandatory reference data;
3. demo/local fixtures.

Departments and employees are clearly fixtures. Decide explicitly whether sex, family status and leave types are mandatory business data or demo values.

In the generator, add a seed classification such as `NONE`, `BASELINE`, or `DEMO`. Do not make every generated CSV load in every environment.

If these changesets have reached persistent databases, do not edit them casually: append corrective migrations or create a deliberate new baseline.

---

## 8. Remove destructive switches from the normal path

Two hazards exist:

- `init.sql` drops the entire `public` schema;
- `application.yml:30` exposes Liquibase `drop-first` through an environment variable.

Recommended action:

- remove `init.sql` from normal starter output, or rename it `reset-local-db.sql`;
- require an explicit local database target;
- remove `SPRING_LIQUIBASE_DROP_FIRST` from shared configuration;
- make reset a separate, conspicuously destructive command.

No normal startup command should be able to erase data.

---

## 9. Define production administrator provisioning

Without the dev Liquibase context, a new installation has no user and no way to authenticate.

Choose one lean solution:

- a documented one-time command that generates a BCrypt hash and inserts an admin; or
- a small, explicitly enabled one-shot bootstrap mechanism that refuses to run when a user already exists.

Do not enable the demo context in production and do not add a full account-management subsystem just to solve initial provisioning.

For public-facing projects, consider external OIDC instead of local password/token issuance—but do not bundle both approaches into every starter.

---

## 10. Add concurrency protection

No entity has `@Version`. Stale clients can silently overwrite each other in:

- `EmployeService.java:38-44`
- `DepartementService.java:36-42`
- `CongeService.java:45-51`

Add:

- a `version bigint NOT NULL DEFAULT 0` migration;
- `@Version`;
- a version field in mutable response/update contracts;
- stale-write handling as `409 Conflict` or `412 Precondition Failed`.

`@Version` alone is insufficient if the client does not return the version obtained by GET.

For this application, a DTO version field is probably simpler than ETag/`If-Match`.

---

## 11. Add missing indexes and integrity rules

PostgreSQL does not automatically index referencing FK columns.

Add:

- `ix_employe_sexe_id`
- `ix_employe_situation_familiale_id`
- `ix_employe_departement_id`
- `ix_conge_employe_code(employe_id, code)`
- `ix_conge_type_conge_id`

Also:

- synchronize sequences after explicit-ID fixture loads;
- add `lower(username)` uniqueness to match case-insensitive lookup;
- add a database check for `date_fin_conge >= date_debut_conge` when both exist;
- consider `ddl-auto: validate` after Liquibase.

Do not add speculative indexes to every text filter. `%value%` searches require PostgreSQL trigram indexes, which should be introduced only after measurement.

# P1/P2 — API contract

## 12. Own the page JSON instead of serializing `PageImpl`

`EmployeResource.java:40` returns `Page<EmployeDto>` directly. Runtime emitted Spring Data’s warning:

> Serializing PageImpl instances as-is is not supported.

Spring Data explicitly recommends against this because its JSON can change across releases.

The frontend currently expects the flat fields `number`, `size`, `totalElements`, etc. Therefore the least disruptive fix is an explicit `PageResponse<T>` preserving the current flat shape. This gives you a stable contract without forcing an immediate frontend rewrite.

Also:

- paginate leave collections;
- paginate/search employee reference lists;
- static, genuinely small lookup lists may remain unpaged;
- remove exposed `Link`/`X-Total-Count` CORS headers if they remain unused.

---

## 13. Validate and map sort properties

Spring Data documentation states that sort properties arrive as unvalidated strings and applications are responsible for checking them.

`PageableUtils` provides stable ordering, which is good, but arbitrary persistence property names still reach JPA.

Generate a small per-resource mapping:

```text
public API name -> entity property
```

Reject everything else with `400`. Keep the `id` tie-breaker.

---

## 14. Fix the Problem Details ownership conflict

Static inspection suggested the catch-all might convert framework errors to `500`, but runtime proved that Boot’s `ProblemDetailsExceptionHandler` currently wins:

- bad ID → `400`;
- unknown route → `404`;
- wrong method → `405`.

However, this also means your custom handlers for:

- `MethodArgumentNotValidException`;
- `HttpMessageNotReadableException`;

are bypassed. Blank login produced no custom `fields` property.

Choose one approach:

1. accept Spring Boot’s default Problem Details and delete the dead custom handlers; or
2. own the contract by extending `ResponseEntityExceptionHandler`, overriding the desired methods, and adding explicit ordering.

Do **not** simply give the current advice highest precedence: its catch-all could then turn framework errors into `500`.

Add a stable `code` property and preserve `status`, `title`, `detail`, `instance`, and field violations.

---

## 15. Align validation, JPA and Liquibase

Liquibase strings are generally 250 characters, while DTOs lack `@Size` and JPA columns default to 255.

Generate matching metadata:

- DTO `@Size(max = 250)`;
- entity `@Column(length = 250)`;
- Liquibase `varchar(250)`.

Then a 251-character request becomes a field-level `400`, not a database `409`.

Use DSL semantics:

- `Email("email")` should generate `@Email`;
- ordinary `Text` should not;
- leave/date ordering belongs to the HR model;
- avoid guessing universal business validation.

---

## 16. Simplify DTO identity and references

Current DTOs expose both:

```text
id
idEmploye / idConge / idDepartement / ...
```

Only `id` is consistently honored, so contradictory requests are possible.

Full DTOs are also reused as compact references, even though reference mappers deliberately set fields annotated `@NotBlank` to null.

Target design:

- one canonical server-owned ID;
- transitional aliases marked read-only if frontend compatibility requires them;
- a truthful compact reference DTO;
- relation input that clearly requires an ID;
- coordinated frontend/generator migration.

Do not create a large DTO hierarchy. One small reference type and an explicit mutable version field are enough.

---

## 17. Add smaller REST improvements

Worth doing after the preceding items:

- remove repetitive controller `try/catch` blocks and centralize translation;
- use explicit `NotFoundException`/`BadRequestException` rather than broad `NoSuchElementException` and `IllegalArgumentException`;
- add `Location` to successful POST responses;
- standardize the leave collection path on a breaking release;
- make package names lowercase in newly generated projects;
- normalize or deliberately preserve whitespace/case for codes and natural keys.

API versioning, PATCH, idempotency keys and HATEOAS are not currently justified.

# Configuration, build and operations

## 18. Introduce a safe base profile and one convenient local profile

Current `application.yml` mixes production fail-closed JWT behavior with local database credentials and CORS defaults.

Use:

### `application.yml`

- required datasource values;
- empty CORS origins;
- required JWT configuration;
- no `drop-first`;
- production-safe defaults.

### `application-local.yml`

- localhost PostgreSQL;
- localhost frontend origins;
- demo Liquibase context;
- loopback server binding;
- local ephemeral signing key.

Avoid requiring a ceremonial `prod` profile: the base configuration itself should be safe.

Replace scattered `@Value` fields with validated configuration records.

# Generator changes

The generated conventions should be fixed in `../engine`, not only in the copied backend.

Relevant ownership:

| Concern | Generator surface |
|---|---|
| DTO IDs, references, version, validation | `BeDtoPrinter`, field implementations |
| JPA lengths and `@Version` | `Field`, `Text`, `Email`, `BeDomainPrinter` |
| Seed contexts and sequence synchronization | `BeLiqTablePrinter`, `BeLiqDataPrinter` |
| FK indexes/check constraints | `BeLiqConstraintPrinter` |
| Controller exception duplication | CRUD `*ResourceInjection` classes |
| Stable page response/sort allowlist | filter/list injections |
| Reference-data registry | generate from `ReferenceData` metadata |
| Project package/app/issuer/database names | a small generator project-settings input |

The current `ReferenceDataService` is allowlisted and not directly injectable, but it is domain-specific, stringly typed runtime code under `app.core`. Generate an explicit switch/repository implementation instead of dynamic entity/property JPQL.

Also add generator verification:

1. clean deterministic generation;
2. golden output comparison;
3. merge the generated backend overlay with `crud-be`;
4. compile it;
5. run its Liquibase migration against PostgreSQL;
6. assert a second generation is byte-stable.

The engine’s comparator-first workflow is good and should be retained.

# Features to keep

Do not lose these strengths:

- package-by-feature domain slices;
- direct, hand-editable generated Java;
- DTO/entity separation;
- service transaction boundaries;
- dirty checking;
- `open-in-view: false`;
- lazy relations;
- entity graphs on collection queries;
- stable pagination tie-breaking and max page size;
- correctly escaped LIKE filters;
- database-backed uniqueness and foreign keys;
- no dangerous cascade deletion;
- Liquibase as the only schema owner;
- stateless bearer authentication;
- exact CORS origins and no credentialed CORS;
- BCrypt cost 12;
- fail-closed production JWT secret;
- sanitized unexpected errors;
- compact Boot-managed dependency set.

---

# Features not to add by default

Avoid turning “best” into “largest”:

- generic base CRUD controllers/services/repositories;
- reflection-driven mappers or reference registries;
- microservices;
- reactive WebFlux for a JDBC application;
- Lombok or MapStruct merely to shorten generated output;
- H2 integration tests;
- generic RBAC engines;
- refresh/revocation infrastructure without a requirement;
- cache, auditing or notifications in every project;
- Kafka/event buses;
- Kubernetes/Helm/service mesh;
- SonarQube, mutation testing or blanket coverage percentages;
- OpenAPI unless an independent client needs it;
- native images without a measured deployment benefit.

Auditing may be essential for a real HR project, but it is a domain/compliance decision, not a universal CRUD starter feature.

# Suggested implementation order

## Phase 1 — verification first, 1–2 days

- test dependencies;
- PostgreSQL Testcontainers;
- security/migration/error/CRUD/filter tests;
- one CI `clean verify` job.

## Phase 2 — immediate hardening, 1–2 days

- filter factor authorities;
- enforce USER/ADMIN rules;
- validate issuer/key/lifetime;
- local loopback profile;
- production-safe base configuration;
- demo migration contexts;
- safe administrator bootstrap;
- remove destructive reset paths.

## Phase 3 — API and persistence correctness, 2–4 days

- stable page response;
- sort allowlists;
- optimistic versioning;
- DTO/JPA/Liquibase length alignment;
- FK indexes and date checks;
- truthful reference DTOs;

## Phase 4 — generator propagation, 2–5 days

- update engine printers/injections;
- generate reference support;
- introduce project settings and fixture scope;
- golden generation and host-compilation tests;
- coordinate frontend ID/page/role changes.

A focused solo developer could bring the core baseline to a strong production standard in roughly **one to two weeks**, without adding enterprise ceremony.
